# HPSR System v1.0.277 — publicação atômica de horários clínicos

## Objetivo
Resolver a origem do problema em que uma disponibilidade médica aparecia como publicada, mas nenhum horário real era criado em `clinical_appointment_slots`, impedindo pacientes em acompanhamento de visualizar vagas no Portal.

## Arquivos alterados
- `src/components/dashboard/DoctorAvailabilityManager.tsx`
- `supabase/migrations/20260820_000060_atomic_clinical_availability_publication.sql`
- `package.json`
- `package-lock.json`
- `src/components/layout/DeveloperCreditsModal.tsx`

## Estruturas reaproveitadas
- `clinical_availability_series`
- `clinical_appointment_slots`
- `clinical_followup_plans`
- `clinical_followup_occurrences`
- `appointments`
- RPC existente `book_patient_followup_slot`

Nenhuma tabela nova foi criada e o Portal continua usando o plano de acompanhamento como vínculo paciente → médico → especialidade.

## Correções
- A publicação agora usa uma única RPC transacional: `publish_clinical_availability`.
- Série e slots são criados na mesma transação; não pode mais permanecer uma série nova sem slots caso a criação dos horários falhe.
- O período informado significa todos os dias entre data inicial e final, sem recorrência semanal implícita pelo primeiro dia.
- A publicação exige uma única especialidade concreta.
- Perfis com várias especialidades deixam de enviar a string completa como especialidade padrão da nova publicação; a interface seleciona uma especialidade válida individual.
- O cálculo civil usa `America/Sao_Paulo` no banco.
- Conflitos de horário do mesmo médico são detectados antes da criação.
- A migration remove somente séries ativas atuais/futuras que não possuam nenhum slot vinculado; séries históricas e séries com slots não são alteradas.
- A RPC de reserva `book_patient_followup_slot` foi alinhada no banco para especialidades compostas/tokenizadas sem criar nova fonte de verdade.

## Migration
- `supabase/migrations/20260820_000060_atomic_clinical_availability_publication.sql`

A migration foi aplicada ao projeto Supabase conectado. A correção de compatibilidade da RPC `book_patient_followup_slot`, presente na migration `20260819_000059_followup_booking_specialty_token_compatibility.sql`, também foi aplicada ao banco conectado porque a função remota ainda estava na definição anterior.

## Compatibilidade
- Dados históricos preservados.
- Nenhuma tabela existente removida.
- Nenhum atendimento reservado/concluído é alterado pela limpeza de séries órfãs.
- O fluxo de acompanhamento continua baseado nas tabelas canônicas existentes.

## Otimizações
A publicação deixa de fazer insert da série + geração JS + upsert dos slots em chamadas separadas. Uma única transação no PostgreSQL reduz estado intermediário, round-trips e risco de inconsistência.

## Validações
- Estrutura real do Supabase inspecionada antes da alteração.
- Confirmado antes da correção que as duas séries futuras mais recentes possuíam zero slots.
- Políticas, índices, FKs e funções de agenda revisados.
- Após aplicação, verificada a existência da nova RPC e a remoção das séries órfãs atuais/futuras.
- Build executado com `npm run build` no pacote de entrega. Resultado: não concluído porque as dependências não estão instaladas no pacote (`sh: 1: next: not found`).
